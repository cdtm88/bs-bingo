<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client WS URL query params → onConnect | playerId query param is unvalidated client input — must only be used to look up server-side state, never trusted as authoritative identity |
| client → WS → onMessage syncRequest | Any authenticated conn can request a full sync; private board data is sent only to that conn (never broadcast) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-01 | Spoofing | onConnect playerId query param | mitigate | Server reads playerId from URL param but only uses it as a lookup key against #pendingSlots and #players (both server-authoritative). A spoofed playerId that doesn't exist in server maps falls through to new-player path — no harm. An attacker who guesses an active playerId and connects first would receive that player's board; acceptable risk for an anonymous meeting game. |
| T-5-02 | Information Disclosure | #sendSyncToConn board payload | mitigate | syncResponse is sent via conn.send() (unicast) never broadcast. Board data is private. syncRequest handler checks conn.state.playerId before calling sendSyncToConn — pre-hello connections are silently dropped. |
| T-5-03 | Elevation of Privilege | #promoteNextHost | mitigate | Host promotion is exclusively triggered by server-side slot expiry in onAlarm — never by a client message. No client can request promotion. The promoted player is the one with the smallest joinedAt (server-set timestamp). |
| T-5-04 | Denial of Service | Slot-hold alarm flooding | accept | A malicious client could repeatedly connect/disconnect to fill #pendingSlots. Mitigation: one slot per playerId (Map semantics deduplicate). At most N concurrent players can have pending slots. Acceptable for a meeting game. |
| T-5-05 | Tampering | #winnerId persistence | mitigate | #winnerId is set server-side at win detection from conn.state.playerId (server-tagged). Clients cannot inject a winner ID via syncRequest — syncResponse reads from #winnerId field. |
</threat_model>
